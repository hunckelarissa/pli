# Манифест: компилятор подмножества PL/I

**Статус:** разработка (скелет `pl1c` + MR001)  
**Версия инструмента:** см. [`VERSION`](VERSION) (`0.1.0-dev`)  
**Дата фиксации концепции:** 2026-07-31 · **код с:** 2026-10-21  
**Проект:** долгосрочный компилятор классического PL/I с траекторией к Subset G

---

## 1. Зачем это существует

Нужен **живой** компилятор полезного классического PL/I — не академический frontend в дерево GCC и не попытка воскресить `pl1gcc` 2007 года как продуктовую базу.

Параллель по духу: **ULM Solaris Modula-2** — амбициозный, долгий, «монстр допустим».  
Отличие по тактике codegen: у PL/I **ранний исполняемый результат через транспиляцию**, чтобы не повторить год без нормальной кодогенерации.

Нейросети ускоряют реализацию нелинейно; архитектура должна быть такой, чтобы через год рост моделей заливал **фичи**, а не заставлял **переписывать фундамент** под новый GCC.

---

## 2. Северная звезда и границы

| | Решение |
|--|---------|
| **Горизонт совместимости** | ANSI/ISO **PL/I Subset G** (X3.74 / ISO 6522) |
| **Вкус языка** | Классический PL/I (F / Optimizer-эра идиомы), не «Pascal с чужим синтаксисом» |
| **Не цель** | IBM **Enterprise PL/I**, полный ANSI full, multitasking industrial, «как z/OS LE» |
| **Наследие pl1gcc 0.0.15** | Только **спека и справочник** в `research/pl1gcc-0.0.15/` (грамматика, scopes, DCL, lookahead). Не порт, не фундамент |

Формулировка продукта:

> Диалект классического PL/I с траекторией совместимости Subset G; парсер с первого дня принимает классическую поверхность (включая keywords-as-names); исполняемое подмножество растёт от узкого MVP к G; до машины — через стабильный portable backend (сначала C).

---

## 3. Главный архитектурный трюк

Две оси **не смешивать**:

| Ось | Политика |
|-----|----------|
| **Синтаксис / парсер** | Широкий, классический, G-направленный **сразу** |
| **Семантика / codegen / runtime** | Узкий MVP **сразу**, растёт к G |

```text
  Вход: классический PL/I (G-траектория, keywords-as-names)
              │
              ▼
       Парсер принимает широко
              │
              ▼
       Семантика: поддерживается / пока нет
              │
         ┌────┴────┐
         ▼         ▼
     codegen C   явная диагностика:
     (MVP→G)     accepted but not implemented
```

**Запрещено:** молча генерировать неверный код для «parse-only» конструкций.  
**Обязательно:** конструкции вне текущего исполняемого уровня → понятная ошибка реализации.

## 4. Стек (долгая игра)

### Выбрано

```text
  PL/I source
       │
       ▼
  Lexer / Parser / (позже) Preprocessor
       │
       ▼
  AST + семантика + типы     ← главный актив
       │
       ▼
  HIR (свой промежуточный IR)
       │
       ▼
  Backend: эмит C  (+ тонкий runtime libpli)
       │
       ▼
  Системный cc (gcc/clang/msvc)  ← не host frontend
```

- **Первый backend:** транспиляция в **C** + runtime на C.  
- **Второй backend (позже):** LLVM IR — когда язык уже живёт.  
- **Не делаем:** GCC langhooks / GENERIC frontend как условие MVP.  
- **Не делаем сейчас:** свой x64 backend для PL/I (это трек ULM Modula-2).

### Почему не «GCC 17 frontend»

Внутренности GCC ломаются каждый major. Стабильность даёт **свой HIR + эмит в C**, а не привязка к будущей версии ядра. GCC/Clang — потребители нашего `.c`, не платформа фронтенда.

### Парсер

- Keywords-as-names (**в том числе в MVP**): `IF THEN THEN THEN = ELSE; ELSE ELSE = THEN;` — валидный целевой класс.  
- Боль грамматики принята сознательно (как инвестиция, аналогичная ULM).  
- Инструмент: решать отдельно; ориентир — то, что тянет контекстную роль слов (свой scanner+parser, ANTLR с предикатами и т.п.). Tree-sitter — скорее для редактора, не ядро компилятора.  
- `pl1gcc` — источник идей по lookahead и keyword-трюкам.

### Роль ИИ

Senior-ускоритель бойлерплейта (AST, тесты, эмит, runtime) при **человеческом рулении архитектурой**. Не замена манифесту и дисциплине must-run.

## 5. MVP

**MVP ≠ урезанный игрушечный синтаксис.**  
**MVP = классический парсер + узкое исполняемое ядро.**

### Парсер (уже амбициозный)

- Keywords as identifiers  
- `PROCEDURE` / `BEGIN` / `DO` / `END` / `IF` / `SELECT`  
- `DECLARE` с основными атрибутами (часть может быть parse-only)  
- Выражения, метки, вложенные scopes  
- Ориентир: классика + путь к G; не Enterprise-хвост  

### Исполнение Level 0 (узкое)

| Включено | Отложено (parse-first допустим) |
|----------|----------------------------------|
| `PROC OPTIONS(MAIN)` / nested PROC по мере готовности | Полный preprocessor (`%IF`, `%DO`, `%PROCEDURE`) |
| `FIXED BIN`, `FLOAT`, `CHAR(n)`; `BIT` осторожно | `FIXED DECIMAL` industrial, `PICTURE` industrial |
| `AUTOMATIC` / `STATIC` / `PARAMETER` (модель передачи — зафиксировать явно) | `CONTROLLED`, сложный `DEFINED` |
| Присваивания, арифметика, `IF`, простые `DO` | Полный `ON` / conditions industrial |
| Минимум I/O: `PUT LIST` / `PUT SKIP LIST` → runtime | Record I/O, полный stream PL/I |
| | `BASED` / `OVERLAY` / `REFER` в codegen (в AST — можно раньше) |
| | Multitasking, AREA/OFFSET industrial |

Критерий успеха MVP: эталонные **must-run** программы → бинарник через `cc`.

## 6. Лестница к Subset G

| Уровень | Смысл |
|---------|--------|
| **L0 — существует** | Must-run ядро + широкий классический parse |
| **L1 — утилиты** | Больше DO/SELECT, массивы, простые структуры, больше builtins, аккуратный `%INCLUDE` / `%REPLACE` |
| **L2 — наследие** | Пересечение с G расширяется; DECIMAL/I/O/preprocessor по приоритету эталонов |
| **G-horizon** | Документированная совместимость с Subset G на заявленном пересечении |
| **За горизонтом** | Enterprise, полный full standard, «как IBM z/OS» |

Совместимость формулировать честно:

> Совместим с Subset G на документированном пересечении; отличия перечислены.

## 7. Классификация эталонов

Каждый тестовый/наследие-файл помечается:

| Метка | Значение |
|-------|----------|
| **must-run** | Должен компилироваться и выполняться на текущем Level |
| **must-parse** | Парсер принимает; codegen может ответить «not implemented» |
| **out-of-scope** | Enterprise / вне G-траектории; не раздуваем scope |

Минимум для старта концепции (примеры духа):

**must-run (L0):**

```pli
HELLO: PROC OPTIONS(MAIN);
  PUT SKIP LIST('Hello, PL/I');
END HELLO;
```

```pli
ADD: PROC OPTIONS(MAIN);
  DCL (A, B, C) FIXED BIN(31);
  A = 2; B = 3; C = A + B;
  PUT LIST(C);
END ADD;
```

**must-parse (уже в MVP парсера):**

```pli
/* keywords as names — классика */
X: PROC OPTIONS(MAIN);
  DCL (IF, THEN, ELSE) FIXED BIN(31);
  IF THEN THEN THEN = ELSE;
  ELSE ELSE = THEN;
END X;
```

**out-of-scope (примеры духа):** multitasking, CICS/DL/I preprocessor, Enterprise-only builtins/атрибуты.

## 8. Что сознательно не выбираем

- Чинить и портировать `pl1gcc` на современный GCC как продуктовую кодовую базу  
- Ждать/целиться в «GCC 17 host frontend», чтобы «меньше переписывать»  
- Полный Enterprise как KPI  
- Свой машинный backend для PL/I параллельно недожатому ULM  
- «Сначала идеальный весь язык, потом когда-нибудь codegen» без must-run дисциплины  
- Tree-sitter как единственное ядро промышленного парсера PL/I

## 9. Связь с ULM Solaris Modula-2

| | ULM Modula-2 | Этот PL/I |
|--|--------------|-----------|
| Судьба | Нативный, божественный, дожимается | Pragmatic transpiler → G |
| Амбиция фронта | Да | Да (классический parse) |
| Codegen | Свой долгий путь | **C рано**, обязательно |
| Риск «монстр без эмита» | Уже принят | Смягчается must-run, не урезанием классики |

Два продукта, два контракта. Не смешивать KPI.
