# Стек и организация большого проекта

**Статус:** черновик к Техническому заданию  
**Связь:** [`MANIFEST.md`](MANIFEST.md), [`LITERATURE.md`](LITERATURE.md)  
**Вопрос документа:** *как* пилить амбициозный компилятор так, чтобы он мог вырасти до сотен тысяч / миллиона строк **без смены фундамента**, и при этом L0 must-run появился рано.

---

## 1. Честно про «миллион строк»

Миллион строк — **потолок ёмкости архитектуры**, не KPI на год.

| Реализм | Ориентир |
|---------|----------|
| L0 (парсер классики + узкий codegen + runtime + тесты) | десятки тысяч LOC, не миллион |
| L1–L2 / путь к G | сотни тысяч возможно |
| «Миллион» | накопленные: компилятор + runtime + тесты + спеки + эмиттерные таблицы + инструменты |

Архитектура должна **выдержать** рост; процесс должен **запрещать** рост без дисциплины (иначе получите не G-компилятор, а свалку).

ULM учит: большой фронт без раннего эмита — боль. Здесь эмит C — **обязательный контур** с начала реализации (когда дойдём до кода), даже при амбициозном парсере.

## 2. Технологический стек (продуктовый)

Зафиксировано манифестом; здесь — рабочая детализация.

| Слой | Выбор | Почему |
|------|--------|--------|
| **Вход** | Классический PL/I, keywords-as-names | Решение продукта |
| **Парсер** | *TBD в TZ* (свой / ANTLR / hybrid); не Tree-sitter как ядро | Нужен контроль контекста keywords |
| **Представления** | CST/parse tree → **AST** → **HIR** | Стабильный актив; backend сменный |
| **Семантика** | Отдельный проход (имя, типы, storage, атрибуты) | Иначе эмиттер станет помойкой |
| **Backend 1** | Эмит **C** (+ `#line` по возможности) | Долгоживущий, отлаживаемый |
| **Runtime** | Библиотека на **C** (`libpli` или иное имя) | DECIMAL/I/O/строки/условия — здесь |
| **Driver** | CLI: `plic` (имя TBD) → `.c` → вызов системного `cc` | GCC/Clang/MSVC = инструменты, не host |
| **Backend 2** | LLVM (позже) | Второй принтер с того же HIR |
| **Не используем** | GCC as language frontend / langhooks | Ломается каждым major |

**Язык реализации компилятора** (фронт на чём писать) — **решение TZ**, не манифеста. Кандидаты для обсуждения на берегу:

| Кандидат | Плюсы | Минусы |
|----------|-------|--------|
| **Rust** | Модули, жёсткие границы, хорош с ИИ, безопасные структуры AST | Кривая; FFI к C-runtime простой |
| **C++** | Близко к runtime/C; привычный compiler-world | Легче размазать архитектуру |
| **C** | Максимальная простота линковки | Больше ручной дисциплины |
| Смешанный (Rust/C++ фронт + C runtime) | Норма для транспиляторов | Два мира в CI |

Рекомендация архитектора на обсуждение: **фронт на Rust или C++ с жёсткими crate/lib границами; runtime только C**. Не смешивать эмиттер и runtime в одну кашу.

## 3. Монорепо: как резать, чтобы не сгнить

Предлагаемая форма (имена пакетов — черновые):

```text
pli/                          # будущий корень продукта (сейчас — концепция)
  MANIFEST.md
  LITERATURE.md
  STACK.md                    # этот файл
  docs/
    tz/                       # Техническое задание
    spec/                     # Формализованная спецификация (по главам)
    decisions/                # ADR: Architecture Decision Records
  refs/
    pl1gcc-0.0.15/            # -> research/pl1gcc-0.0.15 (reference only)
    refs/literature/          # -> research/refs/literature (raw PDFs)
    literature/               # PDF/копии по LITERATURE.md
  compiler/                   # фронтенд компилятора
    driver/                   # CLI, оркестрация пайплайна
    lex/
    parse/
    ast/
    sema/                     # имена, типы, атрибуты, storage
    hir/                      # стабильный IR
    codegen_c/                # эмит C
    codegen_llvm/             # позже, пустой каркас допустим
    diagnostics/              # единый формат сообщений
  runtime/                    # libpli (C)
    include/
    src/
  stdlib/                     # опционально: builtins на PL/I или C
  tests/
    must-run/
    must-parse/
    out-of-scope/             # явные «не наше», чтобы не ползли в scope
    golden/                   # ожидаемый C / stdout
  tools/                      # маленькие утилиты, не ядро
  third_party/                # вендор только с лицензией
```

**Железобетонные границы:**

1. `parse` не знает про C.  
2. `sema` не печатает C.  
3. `codegen_*` не парсит PL/I.  
4. `runtime` не зависит от компилятора.  
5. `refs/pl1gcc` **никогда** не линкуется в продукт.

Нарушение границы = красный флаг в ревью (человеческом или ИИ).

## 4. Пайплайн компиляции (контракт)

```text
  source.pli
      │
      ▼
  lex → parse ──────────────► diagnostics (syntax)
      │
      ▼
  AST
      │
      ▼
  sema (scopes, types, attrs) ► diagnostics (semantic / not-implemented)
      │
      ▼
  HIR  ◄── единственный стабильный вход для backend’ов
      │
      ├──────────────► codegen_c → tu.c + link runtime → exe
      └──────────────► codegen_llvm (future)
```

**HIR** — то, что защищает от «через год всё переписать». Меняются принтеры; HIR эволюционирует версионируемо (см. ADR).

## 5. Как расти до огромного размера без смены фундамента

### 5.1 Спека впереди кода

Порядок артефактов (ваш месяц на берегу — правильный):

```text
  MANIFEST  →  LITERATURE  →  TZ  →  SPEC (по главам)  →  ADR  →  TODO/roadmap  →  код
```

- **TZ** — цели, границы, стек, deliverables, уровни L0–G, критерии приёмки.  
- **SPEC** — нормативный язык (синтаксис, семантика, runtime), с якорями на GC33-0009 / G.  
- **ADR** — короткие решения («почему C первым», «модель параметров L0»).  
- **TODO** — только после SPEC-каркаса, иначе TODO становится ложной спекой.

### 5.2 Вертикальные срезы, не «сначала весь парсер»

Даже при амбициозном парсере поставка идёт **срезами**:

| Срез | Парсер | Sema | Codegen | Runtime |
|------|--------|------|---------|---------|
| S0 | hello/assign/IF + keywords-as-names на ядре | минимум | C для must-run | put/list, старт |
| S1 | DO/SELECT, больше DCL | массивы… | расширение эмита | … |
| S2 | … к G | … | … | … |

Широкий parse **разрешён**, но каждый спринт/этап обязан двигать **must-run** или **явный not-implemented**, а не только процент покрытия грамматики.

### 5.3 Тесты как несущая стена

- `must-run` — CI gate: без зелёного нет merge.  
- `must-parse` — отдельный gate.  
- Golden: ожидаемый фрагмент C и/или stdout.  
- Запрет: новый синтаксис в парсере без теста в одной из трёх корзин.

### 5.4 Диагностика «not implemented»

Единый класс ошибок: конструкция в AST есть, уровень исполнения не готов.  
Это позволяет амбициозному парсеру не врать пользователю и не блокировать must-run.

### 5.5 ADR против «давайте на ходу перейдём на LLVM-only»

Смена фундамента — только через ADR + обновление TZ.  
ИИ не имеет права «顺便» заменить HIR→C на «сразу всё в LLVM» без записи решения.

## 6. Роль нейросетей в большом проекте

| Можно | Нельзя |
|-------|--------|
| Генерировать бойлерплейт AST/HIR, тесты, эмит кейсов | Менять границы пакетов без ADR |
| Предлагать грамматические правила под SPEC | Тащить Enterprise-фичи «раз уж парсится» |
| Писать runtime-функции по SPEC | Линковать pl1gcc в дерево продукта |
| Рефакторить внутри модуля | Переписывать фундамент каждый major gcc |

ИИ = ускоритель **внутри** манифеста/TZ/SPEC. Чем сильнее модели через год, тем важнее **жёстче** контракты, иначе скорость размножит хаос.

## 7. Инструменты разработки (контур, не религия)

Минимальный инженерный контур (уточнить в TZ):

- Git + code review дисциплина  
- Сборка: CMake или cargo(+cc) / аналог — один вход `build`  
- Форматтеры/линтеры на языке фронта  
- CI: must-parse + must-run на каждой сборке  
- Один «демо» скрипт: `plic hello.pli && ./hello`  
- Каталог `docs/decisions/` с нумерацией ADR-0001…

Отладка транспилятора: **смотреть `.c`**. Это преимущество стека, его надо сохранить (флаг dump).

## 8. Оценка объёмов по подсистемам (порядок, не смета)

| Подсистема | Характер роста |
|------------|----------------|
| Lex/parse | Быстрый рост рано (ваша ставка), потом стабилизация |
| Sema + таблицы атрибутов | Долгий рост к G |
| HIR | Относительно компактный, если не размазывать |
| codegen_c | Рост с семантикой; таблицы соответствий типов |
| runtime | Рост с builtins/I/O/DECIMAL — может стать «вторым компилятором» |
| tests + golden | Часто **больше** кода компилятора — так и надо |
| docs/spec | Месяцы берега; потом постоянное сопровождение |

Именно поэтому монорепо режется так: runtime и tests — граждане первого класса, не «потом навалим».

## 9. Связь с ULM Modula-2 (процесс)

| Практика ULM | Переносим в PL/I | Не переносим |
|--------------|------------------|--------------|
| Долгое вычитывание / амбиция фронта | Да | — |
| Год без нормальной codegen | — | **Да, не повторяем** |
| Нативный backend | Остаётся в ULM | Не параллелим для PL/I |
| «Монстр» | Парсер+SPEC могут быть монстрами | Эмит C должен жить с L0 |

---

## 10. Одной фразой

> **Монорепо с жёсткими фазами AST→sema→HIR→C; runtime на C; pl1gcc только в refs; рост к G вертикальными срезами под SPEC; миллион строк — ёмкость тестов+runtime+компилятора, не цель первого года; ИИ работает внутри границ, фундамент меняется только через ADR.**
